# Skill: качество кода и производительность

## Зачем

Найти в шаблоне то, что ломает обход или INP/LCP. Не рефакторить
весь фронт.

## Когда

- Tech-only, полный аудит после P0.
- CSR-спа, тяжёлые виджеты, магазины на конструкторах.

## Когда не

- Нет HTML и нет репозитория — только внешние догадки, помечай ❓.

## Шаги

1. View-source / сохранённый HTML: есть ли текст оффера.
2. Если SPA: есть ли пререндер/SSR на money-URL. «Робот Google умеет JS»
   не спасает Яндекс и AI-ботов в полной мере — не обещай, что «все прожуют».
3. Дубли: `?utm`, сорт, print, фасеты. Canonical и/или noindex.
4. Пагинация: rel-логика или нормальные URL; без бесконечного crawl.
5. 404 = 404. Корзина / поиск не индексировать без нужды.
6. Вес: герой, шрифты, слайдеры autoplay, четвёртый чат.
7. Третьи скрипты: список, что грузится до interaction.
8. Отдай измеримое в `pagespeed`; сюда — причину в коде.
9. Одна правка-гипотеза лучше десяти «надо бы».

## Входы

- HTML / репозиторий (если пользователь открыл)
- `checklists/code-perf-security.md`

## Выходы

- Список дефектов шаблона с файлом/селектором, если виден
- Что не смотрели (сервер, CDN, RUM)

## Мини-выход (вставить в отчёт)

```
Шаблон: [URL]
Текст в первом HTML: да/нет
Канон/фасеты: …
Третьи скрипты до input: …
Связка CWV: см. pagespeed (field/lab)
```

## Типичные находки

- SSR главной, CSR каталога — money как раз в каталоге.
- Facet URL в sitemap.
- Чат + heatmaps + A/B + три пикселя до first input.
- `<img src="photo.png">` без размеров, CLS гарантирован.

## Как писать evidence

Путь файла или селектор, если репозиторий открыт.
Иначе — цитата HTML и URL. Не выкладывай `.env` из репо в отчёт.

## Ошибки агента

- «Переезжайте на другой фреймворк» как первый next.
- Править всё, кроме канона и SSR.
- Гонять Lighthouse до 100 вместо field-INP.

## Стоп

- Переписывать архитектуру «на Next, потому что SEO» без evidence.
- Минифицировать чужой прод без репозитория.
